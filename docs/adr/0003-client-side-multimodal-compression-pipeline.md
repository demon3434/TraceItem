# 0003: 全模态媒体附件管道规范（JPEG兼容、x265/HEVC视频压缩、Moov挪头与秒开Seek对齐）

## 上下文与决策背景
在物品留痕与查找场景中，用户不仅需要拍摄多张照片，还需要录制语音备忘以及拍摄展示抽屉、暗格行进路径的短视频。原系统（`WhereIsIt`）仅支持单张图片且由服务端做简单压缩，在移动蜂窝网络或公网 DDNS 环境下存在以下痛点：
1. 缺少语音和视频支持，对复杂收纳环境的记录能力弱。
2. 手机拍摄的原生 4K/1080p 视频体积巨大（30MB~100MB），在家庭宽带上行带宽有限（公网 DDNS/端口转发）的场景下，远程播放极度卡顿，拖拽进度条经常假死或黑屏等待数秒。

经决策，建立统一的全模态端侧媒体压缩与流媒体自适应管道，涵盖图片（JPEG）、音频（AAC）与短视频（x265/HEVC）。

## 架构决策与选型理由
1. **多模态录入双通道支持**：
   - 移动端对图片、视频、音频三大类附件，均同时支持**“实时采集”**（App 内直接拍照、拍视频、录制语音）与**“本地导入”**（从手机系统相册挑选照片/视频、从系统录音文件夹选择已有音频文件）。
2. **图片存储格式：统一采用 JPEG**：
   - 客户端（移动端/Web）在上传前对图片进行智能等比缩放（限制最大长边 1600px），压缩格式统一采用 **JPEG**（质量 80%~85%），兼顾极佳的跨平台编解码兼容性与高画质，单图压缩至 150KB~350KB。
3. **视频附件优先采用 x265 (HEVC) 编码**：
   - 在相同画质下，x265 比 x264 码率节省近 40%~50%，10 秒空间寻路视频体积压缩至 1MB~2MB。
4. **Moov Atom 前置移头（FastStart）**：
   - 视频封装必须将 `moov` 元数据索引块放置于文件头部（`+faststart` / `qt-faststart`），避免播放器必须下载完整个视频才能解析播放的缺陷，实现公网 HTTP 流式秒开。
5. **GOP 关键帧（Keyframe）间隔锁定与 Seek 优化**：
   - 视频编码时严格设定固定关键帧间隔（如 `keyint=30/fps=30`，每 1 秒强制插入一个 I 帧 / IDR 帧），配合客户端播放器（Media3/ExoPlayer 的 `CLOSEST_SYNC` 对齐），彻底消灭公网拖动进度条时的解码卡顿，实现毫秒级响应拖拽。
6. **语音备忘格式**：
   - 单声道 AAC/M4A 48kbps，时长上限 60 秒，体积约 350KB/分钟。

## 用户补充细节
> **专栏：用户针对该项提出的补充与扩展**
- **图片格式明确要求**：无论在移动端还是 Web 端，图片均可保存为 **JPEG**，确保所有终端查看时的免转码兼容性。
- **采集来源双规**：明确要求 3 种多媒体附件均需支持“拍照/拍视频/实时录音上传”以及“从手机的相册、录音目录导入上传”两种途径。
- **视频编码硬指标**：视频附件优先使用 **x265 (HEVC)** 编码，大幅削减家庭 NAS 存储与移动端流量。
- **公网播放防卡顿与秒开防线**：视频必须兼顾公网访问体验，绝不能卡播放进度条。必须将 **MOOV 索引块放在文件最前面**（FastStart），且必须设置**明确的关键帧（Keyframe）**，确保公网播放时拖拽进度条能迅速定位起播。
- **存储生命周期**：物品删除时物理媒体附件级联硬删除，保持家庭服务器小巧无冗余。
