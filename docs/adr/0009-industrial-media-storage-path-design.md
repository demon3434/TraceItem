# 0009: 多媒体附件存储路径的现代工业化分层与分片设计

## 上下文与决策背景
在原有系统（`WhereIsIt`）中，所有上传图片均被粗暴地扁平散落在单一的 `/uploads/` 根目录下，文件名为简单的 `u1_i1_uuid.jpg`。
这种原始设计在现代软件工程中存在严重的工业化缺陷：
1. **目录索引性能雪崩**：当家庭累计拍摄数千至数万张照片、短视频与录音时，单个目录下的文件数急剧膨胀，导致底层文件系统（Linux ext4、Windows NTFS 等）在进行 `readdir`、索引遍历和备份归档时 I/O 性能呈断崖式下跌。
2. **类型混杂与流媒体分发困难**：图片、音频、短视频及其生成的缩略图混杂在同一文件夹，无法针对不同媒体类型施加差异化的 HTTP 缓存头（如图片强缓存 1 年、视频启用 `Accept-Ranges` 分段流媒体传输）。
3. **备份与增量维护不便**：缺乏时间维度的组织，无法快速定位或归档特定历史时期的媒体资产。

经决策，确立**严格符合现代工业化标准的多媒体存储分层、按类型分流与时间哈希两级目录分片规范**。

## 架构决策与选型理由
1. **顶级类型与职责物理分流**：
   - 存储根路径统一挂载于 `/data/media/`。
   - 一级子目录严格按媒体实体类型解耦：
     - `/data/media/images/`：存放全尺寸压缩后的 JPEG 物品照片；
     - `/data/media/audios/`：存放 AAC/M4A 语音备忘录音；
     - `/data/media/videos/`：存放经过 x265 转码与 MOOV 前置处理的 MP4 空间短视频；
     - `/data/media/thumbnails/`：存放所有媒体对应的极速加载封面与缩略图。
2. **时间维度两级目录分片（Time-Partitioned Sharding）**：
   - 杜绝单目录文件膨胀，采用现代工业通用的 `YYYY/MM/` 年月分片结构：
     `media/{type}/{YYYY}/{MM}/{file_name}`
   - 示例：
     - 照片：`/data/media/images/2026/11/img_0192e4ab_8f21_7000.jpg`
     - 视频：`/data/media/videos/2026/11/vid_0192e4ac_3d12_7000.mp4`
     - 视频封面：`/data/media/thumbnails/videos/2026/11/vid_0192e4ac_3d12_7000_poster.jpg`
     - 录音：`/data/media/audios/2026/11/aud_0192e4ad_9a44_7000.m4a`
3. **基于时间有序 UUIDv7 / Nanoid 的命名体系**：
   - 文件名采用带有类型前缀与时间顺序特性的哈希命名（如 `img_`、`vid_`、`aud_` 加上自带高精度时间戳的 UUIDv7）；
   - 天然具备防碰撞、跨平台兼容性、按时间物理排序特性，且不泄露家庭成员隐私信息。
4. **Nginx / FastAPI 静态分发与缓存加速**：
   - 结构清晰映射至 HTTP 访问 URL：`/media/images/2026/11/...`；
   - 方便在反向代理（如 Nginx）中直接对 `/media/` 统一配置 `sendfile on;`、`tcp_nopush on;` 以及流媒体切片分发。

## 用户补充细节
> **专栏：用户针对该项提出的补充与扩展**
- **明确工业化设计标准**：“另外，多媒体附件的存储路径，要符合现代软件的工业化设计。”
- **杜绝单目录平铺滥用**：严禁采用历史遗留的将成千上万个文件散落在一个目录的做法，必须具备清晰的类型隔离、分片扩展性与高性能读写能力。
