# 0006: 集成式 TAR 纯打包备份、历史清理与单文件小于500行工程规范

## 上下文与决策背景
原架构设想中采用 ZIP 压缩算法生成系统备份，并设计了定时自动备份逻辑。经过审视与用户实际家庭使用边界约束，发现：
1. **压缩算力开销冗余**：多媒体附件（JPEG 图片、AAC 音频、x265 视频）在上传端已经过深度有损压缩，再次执行 ZIP 压缩几乎无法缩小体积，反而白白耗费家庭低功耗 CPU（如树莓派、工控机、低配 NAS）的算力与时间，造成备份时整机卡顿。
2. **定时任务不可控**：家庭自建服务不需要无休止的后台定时器，定点执行反而可能干扰正常使用。
3. **磁盘膨胀风险**：若只增不减，历史备份文件会持续吞噬宝贵的本地存储空间。

经决策，重构备份与代码治理方案：**采用零 CPU 算力消耗的 TAR 纯归档流（无压缩）、仅由 Admin 手动触发备份、内置完备的历史备份清理机制，并严格坚守单文件代码行数小于 500 行的工程底线**。

## 架构决策与选型理由
1. **无压缩 TAR 极速纯打包**：
   - 备份格式统一为 `.tar`。
   - 底层仅做文件流的连续串联打包（包括一致性 SQLite 镜像 `antusuoji.db`、`manifest.json` 与 `media/` 媒体流），CPU 占用率接近 0%，速度受限于磁盘 I/O，秒级完成备份包生成与下载。
2. **Admin 纯手动备份工作流（免定时器）**：
   - 彻底移除后台定时备份 Cron/Celery 依赖，降低服务端架构复杂度。
   - 仅在 Admin 管理面板提供“立即生成系统备份”操作按钮。
3. **历史备份生命周期与清理机制 (Backup Pruning)**：
   - 提供 `GET /api/admin/backups` 列表查看接口（展示文件名、创建时间、文件大小、校验哈希）；
   - 提供 `DELETE /api/admin/backups/{filename}` 接口与 Web 界面单项/批量删除按钮；
   - 支持设置“保留最新 N 份备份”（如默认保留最近 5 份，生成新包时自动淘汰旧包），彻底杜绝磁盘无休止膨胀。
4. **单文件小于 500 行代码规范**：
   - 全端（Python/Flutter/Vue）强制模块化，拆解 Router、Service、Repository 与 UI 组件，杜绝巨型单体文件。

## 用户补充细节
> **专栏：用户针对该项提出的补充与扩展**
- **拒绝 ZIP 压缩算力消耗**：“我不希望通过zip压缩，引入不必要的算力消耗。直接tar打包就行。”
- **免定时器纯手动**：“而且也不需要做定时备份，只需要admin手动备份。”
- **必须具备历史清理功能**：“需要设计清理历史备份记录的功能，不能无休止地增加tar备份包。”
- **单代码文件行数红线**：“单个代码文件不要超过500行，逻辑要解耦，尽量拆分。”
- **多端精美UI统一与借用**：“我希望做出来的web页面也手机端UI，要尽量精美，我希望能借用；软件界面风格统一。”
