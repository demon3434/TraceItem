# 0001: 采用 SQLite WAL 模式与 FTS5 替代 PostgreSQL

## 上下文与决策背景
原有系统（`WhereIsIt`）采用 PostgreSQL 16 关系数据库，在家庭 NAS、轻量云服务器或工控小主机（如群晖、威联通、树莓派）上部署时存在以下痛点：
1. 必须单独启动 PostgreSQL 守护容器，常驻内存消耗高达 150MB~300MB。
2. 备份与恢复依赖 `pg_dump` 和客户端工具（如 `WhereIsIt-Bak`），流程复杂繁琐。
3. 家庭收纳属于低并发（通常 1~5 个家庭成员）、中小数据量场景（极少超过 50,000 件物品）。

经决策，服务端数据库彻底替换为**内嵌式 SQLite 3，全面开启 WAL（Write-Ahead Logging）模式，并利用内置 FTS5 引擎提供中英文字符全文索引**。

## 架构决策与选型理由
1. **零外部依赖与极低开销**：SQLite 作为进程内轻量数据库，无需独立守护进程与网络端口，内存占用压低至 15MB 以内。
2. **WAL 模式保障并发读写**：开启 `PRAGMA journal_mode = WAL;` 与 `PRAGMA synchronous = NORMAL;` 后，写操作不会阻塞读操作，完美支撑家庭多成员同时浏览与多设备并发查询。
3. **极简备份恢复**：数据库本身为一个单一文件（`antusuoji.db`），系统备份与恢复无需任何额外数据库命令行，仅需文件拷贝或执行 `VACUUM INTO` 即可生成一致性冷备快照。
4. **内置 FTS5 引擎**：无需引入复杂的搜索引擎中间件，直接通过 SQLite FTS5 虚拟表提供针对物品名称、品牌、位置细节与备注的高速检索。

## 用户补充细节
> **专栏：用户针对该项提出的补充与扩展**
- **家庭与轻量场景边界**：明确本系统定位为家庭自用与个人收纳管理，不考虑数万并发的高并发互联网场景，数据库复杂度降维。
- **历史数据平滑演进**：放弃原项目中沉重的外部 DB 依赖，但需提供针对旧版本数据（PG16 导出 JSON 及离线版 Room SQLite）的轻量导入解析能力，避免历史数据丢失。
- **外键约束显式激活**：SQLite 默认不强制检查外键，连接初始化必须显式执行 `PRAGMA foreign_keys = ON;` 以确保空间、物品与附件关系的级联完整性。
